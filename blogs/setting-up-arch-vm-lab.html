Setting Up a Little VM Lab on Arch, for School

21 September 2026 · Virtualization · ~8-10 min

Every semester I tell myself I’m going to keep my main Arch install clean. But with my 2nd year coming up, I decided to compartmentalize my work.

This semester I ended up setting up three virtual machines.

The setup itself was straightforward for the most part. For the "MOST" part. (foreshadowing)

Step one: does my CPU even do this?

Before installing anything, I wanted to make sure the hardware supported hardware-accelerated virtualization.

lscpu | grep -i virtualization

It came back with VT-x, so Intel hardware virtualization support was there.

Building the toolbox

I installed the main pieces I knew I would need:

sudo pacman -S qemu-full libvirt iptables-nft dnsmasq virt-manager

I went with qemu-full instead of the base qemu package because I have some RISC-V projects coming up and didn’t want to redo the setup later.

libvirt gives me a way to manage the VMs without having to build every QEMU command by hand. iptables-nft replaces the legacy iptables setup, and dnsmasq handles the networking side so the VMs can actually get out to the internet.

Then there’s virt-manager, mostly because I didn’t want to be typing virsh commands for three different machines.

After that, I enabled and started libvirtd and added myself to the appropriate group so I wouldn’t have to use sudo for everything.

At that point the basic VM setup was ready.

The lineup

I ended up with three VMs, each for a different reason:

  • Debian for COMP2406. Some of the course software doesn’t cooperate particularly well with Arch, and I’d rather use a VM than spend time trying to force everything through the AUR. And with the recent news about thousands of malicious packages on AUR, I rather not.
  • Kali for CTFs and other security projects.
  • A headless Ubuntu VM for COMP2401. Carleton provided this one as a pre-built .ova.

The Ubuntu VM was the easy one. The Debian VM was the one that turned into a debugging session.

COMP2401: unpacking someone else’s VM

An .ova is basically a tar archive containing the files needed for the virtual machine.

tar -xvf comp2401.ova

That gave me a .ovf, a .vmdk, and a .mf.

The .vmdk is the actual disk image. libvirt can technically work with VMDK directly, but I wanted it in qcow2 format, since that integrates more cleanly and performs better with it.

qemu-img convert -f vmdk -O qcow2 comp2401.vmdk comp2401.qcow2

Before creating the VM, I also looked through the .ovf to see what Carleton had actually configured it for. It was set up with 2 GB of memory and 3 CPUs, so I didn’t have to guess at the intended hardware.

From there, it was just virt-manager:

New Virtual Machine → Import existing disk image → select the qcow2 → Ubuntu 26.04

That part was easy enough that I figured the Debian VM would probably be similar.

It wasn’t (LOL).

COMP2406: where things got interesting

Debian installed normally until it needed to reach a mirror for anything beyond the base installation.

It kept getting stuck at the scanning part, so I figured that the internet on the VM was not configured properly.

My first thought was bridging. The interface libvirt was using was named virbr0, and I initially read that as “virtual bridge,” (which I mean... it is named that...) so I assumed I had a bridging problem.

That turned out to be wrong because I hadn’t worked with networks for long enough.

virbr0 is libvirt’s default NAT network, not a bridge.

Once I ruled that out, I had two things I wanted to check: whether IP forwarding was enabled on the host, and whether my nftables setup was interfering with libvirt’s NAT rules.

Rather than guessing, I checked each piece.

First:

ip a show virbr0

The address and subnet were there and looked correct.

Then:

virsh net-list --all

The default network was active.

Then I checked IP forwarding:

cat /proc/sys/net/ipv4/ip_forward

That returned:

1

So forwarding was enabled.

That left the firewall setup as the main suspect.

I switched to tty2 from inside the Debian installer with Ctrl+Alt+F2, dropped into a shell, and tested whether the VM could reach an external IP directly:

ping -c3 1.1.1.1

What surprised me was that the initial connection was made, but then every attempt after resulted in no packets coming through (100% packet loss?)

The actual culprit

After 2 hours of manual debugging, I had to take the help of AI agents to debug this situation because I was going crazy. So... I already had Docker for one of my other projects. Docker was also managing firewall rules on the host. It creates its own filter table and its own FORWARD chain, with a default drop policy. Forwarded traffic on the host can end up going through Docker’s filtering chains, and those chains explicitly allow traffic for Docker’s own interfaces, such as docker0 and its other bridge networks.

virbr0 wasn’t included, so traffic coming from the libvirt network was being dropped there.

What made this confusing was that libvirt’s own forwarding rules were fine. The libvirt network had the correct accept policy and was configured to forward traffic properly. The problem was that Docker’s chain was also involved, and a drop from that path still meant the packet was rejected before it could get where it needed to go.

That also explained something else I had noticed: DNS appeared to work even though pinging an external IP did not.

libvirt’s dnsmasq serves DNS directly on virbr0. Those DNS requests don’t have to leave the host to be answered, so they don’t need to pass through the same forwarding path.

Internet traffic is different. Once the VM tries to send something out through the host, the packet has to be forwarded, and that was where Docker’s rules were getting in the way.

The fix was to use Docker’s DOCKER-USER chain, which is intended for custom firewall rules and persists across Docker restarts.

I added:

sudo iptables -I DOCKER-USER -i virbr0 -j ACCEPT
sudo iptables -I DOCKER-USER -o virbr0 -j ACCEPT

Then I ran the same test again:

ping -c3 1.1.1.1

This time it worked. I don’t really know if this was a good solution, or a temporary solution, but it worked none the less.

What’s next

At this point both of the important VMs are working. Debian can pull packages normally, and the Ubuntu VM boots headless as expected. Kali is still left to set up.

The next thing I want to do is get sshfs working so I can access and edit the COMP2401 VM’s files directly from my Arch host instead of working through the terminal inside virt-manager.

That’s probably the next part of the setup, which I’ll make another blog post :V
